# FP6 device tree bindings for the 5.0 vendor drivers

The FP6 device tree is the 6.1 one (Fairphone and Qualcomm's 6.1 bindings). The kernel is GrapheneOS's
kernel_common-6.18 with Qualcomm's KERNEL.PLATFORM.5.0 vendor modules ported to it. Where a 5.0 driver (or the 6.18
core) reads a binding differently from the 6.1 tree, the node needs a source change. Qualcomm publishes no volcano
device tree for 6.6 or 6.12, so the 6.1 tree stays the source and the changes sit in `vendor/fps_overlay/fp6.dts` (and
in the volcano techpack files for techpack nodes). This file lists the changes, how to build and check the tree, and
what every node with a compatible was checked against.

## Build and check

```
dts/scripts/build-fp6.sh KERNEL_COMMON OUT      builds the base, the SKU overlays and the techpack overlays
python3 dts/scripts/check-bindings.py OUT       asserts the bindings listed below on OUT/fp6-sku-608.dtb
python3 dts/scripts/dtdiff.py A.dtb B.dtb       compares two blobs by content
```

- `KERNEL_COMMON` is a kernel_common-6.18 tree. A sparse checkout is enough:
  `git archive HEAD scripts/dtc include/dt-bindings include/uapi/linux/input-event-codes.h`.
- The script compiles with that tree's dtc (1.7.2) and its `include-prefixes`, with `dts/include` first so the vendor
  headers win, then merges with `scripts/merge_dtbs.py` as the 6.1 build did. It needs cc, flex, bison, make, python3
  and fdtget/fdtput on the PATH. It builds dtc from `KERNEL_COMMON` and fdtoverlay and fdtoverlaymerge from
  `qcom-dtc/`. The merge needs Qualcomm's fdtoverlay: the 6.18 libfdt inserts each added subnode before the existing ones, which
  reverses the children of 62 parents. `TOOLS=OUT/bin` of an earlier build skips that step. A build takes about 40 seconds.
- `OUT/fp6.dtb` is the base the bootloader hands to the kernel (vendor_boot). `OUT/fp6-sku-N.dtb` is that base with the
  overlay of SKU N applied, which is what the kernel sees. The overlay used is the one that carries the MTP techpack
  parts (audio, camera, display), as the phones use. The audit reads SKU 608.
- `dtdiff.py` matches nodes by path and properties by name. Two properties are equal when their bytes are equal or when
  every cell is equal or is a phandle to the same node path in both trees. The children of each node must come in the same
  order (`--no-order` skips that). It prints one line per difference.
- Each check in `check-bindings.py` names the driver it asserts for. A check fails on a build made before its fix and
  passes after it.

### What a phone test should look at

- C1: UFS comes up (`dmesg | grep -i ufs`, no wait for the `ufs_dev` cell) and no nvmem error for the SDAM. The
  modem remoteproc starts and `dmesg` has no "Unable to get the CMA area". `dmesg | grep -i cpucp` shows the mailbox
  probed without a missing `tx` or `rx` region.
- C2 and C8: the core warns once per boot (a `WARN_ONCE` in `of/base.c`), so a clean `dmesg` proves little. Only the first
  parent without cells would ever show. The `explicit-cells` scan covers every node with a `reg`, which is what to rely on.
  A "Missing '#address-cells'" line naming a parent would mean a node the scan does not see.
- C3: `dmesg | grep -i ramoops` reports the region at 0x9fe000000. After a reboot `/sys/fs/pstore` holds the console
  record.
- C4: `dmesg | grep -i sync_state` shows the interconnect providers finishing. In suspend the SoC reaches AOSD and
  CXSD (sleep statistics).
- C5 and C9: with a card inserted `dmesg | grep mmc1` shows the card, the card mounts, and removing it is noticed. With the card
  in use `/sys/kernel/debug/regulator/regulator_summary` shows `pm7550_l13` at 2960 mV and `pm7550_l23` at 2900 mV for 3.3 V
  signalling (1800 mV after a UHS card switched). Read a large file for the speed.
- C6: the "error finding dst node" line for the USB controller is gone from `dmesg`. With USB connected
  `/sys/kernel/debug/interconnect/interconnect_summary` lists the USB controller (`a600000.ssusb`) below `qhs_ipa`. USB
  enumeration and charging are unchanged. The votes on that path are small.

## How the audit was done

The audit covers every node with status `okay` (or no status) and a compatible in the merged tree (the base with the
SKU 608 overlay applied): 696 nodes. They fall into 324 groups (same compatible list and same driver), one row
each in the table below. Thirteen nodes sit under a disabled parent and are listed too.

1. A script matched each compatible with the match tables of the vendor modules under `modules/` and the 6.18 core
   (kernel_common-6.18 at `03c6a8d2a`), collected the property reads of the driver (`of_property_read_*`,
   `of_get_property`, `of_find_property`, regulator, clock, reset, interconnect, interrupt, reg, dma, nvmem-cell, mbox and
   pinctrl names, memory-region indexes, phandle argument counts, child node names) and compared them with the node in
   both directions. It also compared the node with its sibling nodes in Qualcomm's 5.0 trees.
2. Every group was then checked by reading the driver's probe and parse code, because the script is a regex pass: it
   misses reads made through helpers and compatibles built by macros, and it flags reads that belong to other node types
   of the same module.
3. The tree-wide facts were checked by script: every interconnect pair against the nodes its provider has (238 pairs),
   every clock and reset reference against the driver's clock array (242 uses), every TLMM pin group and function, the
   SPMI GPIO pin states, the RPMh regulator mode maps (39 nodes), phandle argument counts, and supplies that point at a
   disabled node.

Reference for the binding a 5.0 driver expects: Qualcomm's 5.0 device trees for sibling SoCs
(`clo/la/platform/vendor/qcom-opensource/devicetree`, tag `KERNEL.PLATFORM.5.0.r48-00400-kernel.0`, path `qcom/`). Only
pineapple, sun and the shared PMIC and SMMU files were fetched (about 150 files, 1.7 MB). There is no volcano or cliffs
tree in 5.0. The audio, camera, display, GPU, video, WLAN, Bluetooth, NFC, data and DSP trees are techpack projects
that are not in that repository, so for those nodes the driver source is the only reference.

Limits of the audit:

- Several vendor drivers are 6.1 sources, not 5.0 ones: the Bluetooth power driver (`btpower`), the WLAN platform driver (`icnss2`), the
  eswin touch driver, the hall sensor, the haptics, the focaltech fingerprint driver, `sec_nfc` and the ToF sensor. They read what the
  6.1 tree has. The thermal and DCVS set and most of the peripherals set are 5.0 sources.
- Nodes that only exist in the SKU overlay were read against their drivers too. A fix for them would have to go into the
  overlay, which was not changed. See F23.
- Source reading cannot show how a driver behaves on the hardware. Where a node fits the driver structurally and only the
  hardware could settle it, the row says so and the question is a finding.
- A fix was made only where the driver's behaviour and the value were certain. Everything else is a finding below.

Paths: vendor driver paths in the table are relative to `modules/`. Core driver paths (`drivers/...`, `fs/...`,
`kernel/...`) are in kernel_common-6.18. `bindings-50-nodes.tsv` lists every node with its row number.

### Result

324 groups: 257 ok (some with a note or an earlier fix), 1 fixed in this audit, 16 with a finding, 50 with no driver in the 6.18 set.

## Findings

Findings are mismatches or doubts that were not fixed. Each says where, what is uncertain and what a phone test should
look at.

**F1. GPU CX and GX supplies (ok).** `modules/gpu/graphics-kernel/kgsl_pwrctrl.c:2299-2305` reads `vddcx-supply` and `vdd-supply` from
the GPU node, which has neither, and the GMU node carries both. That is right for gen8: `adreno_gen8_gmu.c:2009` calls
`kgsl_pwrctrl_probe_gdscs` with the GMU device, which takes the two supplies from the GMU node (`kgsl_pwrctrl.c:1817-1850`) and
holds them there. The same two supplies on the GPU node would add a second consumer and unbalance the GDSCs, so nothing changes.

**F2. GPU power level bin follows the SoC feature code.** `qcom,gpu-pwrlevel-bins`, `modules/gpu/graphics-kernel/adreno.c:880-940`
(bin choice) and `:1045-1068` (code from socinfo). Bin 0 (10 levels, top 1.15 GHz) matches only particular feature codes. Bin 1
lists 0x2 and 0x0, and a 0 in the list matches every code, so it is the catch-all. A phone whose code is outside bin 0
runs on the lower bin without an error. The choice also needs socinfo loaded before kgsl. Phone: read the maximum GPU
frequency (`/sys/class/kgsl/kgsl-3d0/max_gpuclk`) and compare with the two bins in `volcano-gpu-pwrlevels.dtsi`. "No match
for speed_bin" in `dmesg` would mean both bins failed.

**F3. Display catalog values.** `/soc/qcom,mdss_mdp@ae00000` (`qcom,sde-kms`), `modules/display/display-drivers/msm/sde/sde_hw_catalog.c:594-760`
(property tables), `:5101` (volcano target), `msm_drv.c:2102-2135`. All 13 required catalog properties exist, the bus names and
vote tables have the sizes the 5.0 code expects and the volcano target is known (SDE 10.2.0). The counts and offsets (4 sspp,
5 mixers, 4 intf, 2 dsc, 5 pp) cannot be checked against the display hardware from source. 108 optional properties the 5.0
tables read are absent (for example `qcom,sde-sspp-clk-ctrl`, `qcom,sde-vig-hsic`, the dspp features). They were absent in
6.1 too and decide clock gating and colour features, not probe. Phone: `dmesg | grep -i "sde\|dsi\|msm_drm"` for catalog or
"failed to get" lines. A black screen, flicker or a first-frame hang at boot would point here.

**F4. dwc3 clock gating property.** `/soc/ssusb@a600000/dwc3@a600000`. `snps,disable-clk-gating` is read by neither
`drivers/usb/dwc3/core.c` (properties at `:1763-1845`) nor `modules/base/drivers/usb/dwc3/dwc3-msm-core.c`. The 5.0 downstream
core read it, the GKI core does not, so the controller keeps default clock gating. Not a device tree fix, it needs a core
patch if the FP6 needs gating off. Also unread and harmless: `snps,ssp-u3-u0-quirk` (pineapple has it, volcano does not),
`qcom,iommu-dma*`. Phone: USB resume with the screen off, unplug and replug, role switch with an OTG device, and
`dmesg | grep -i dwc3` for timeouts.

**F5. SMMU QTB register address.** `anoc_2_qtb@171a000` has `reg = <0x171b000 0x1000>` while pineapple has 0x171a000 and
every other QTB's unit address equals its `reg`. `modules/base/drivers/iommu/arm/arm-smmu/arm-smmu-qcom.c:1500,1561`. The 6.1
volcano tree has 0x171b000 as well, and the sources cannot say which is the SM7635 block. It affects TBU halt, ATOS and
fault debug, not normal DMA. Phone: SMMU fault reports for the ANOC 2 master, and a clean `dmesg` after camera, display and
video use.

**F6. Clock references the volcano clock drivers do not register (harmless).** `GCC_CAMERA_AHB_CLK` (12), `GCC_DISP_AHB_CLK` (22),
`GCC_GPU_CFG_AHB_CLK` (32), `GCC_VIDEO_AHB_CLK` (155) and `GPU_CC_GX_AHB_FF_CLK` (17) are named by the camcc, dispcc, videocc,
gpucc and seven GDSC nodes but `modules/base/drivers/clk/qcom/gcc-volcano.c` and the gpucc driver do not register them (same
in 6.1). The consumers get a NULL clock, which is harmless: the probes switch all five branches on for good
(`gcc-volcano.c:3446-3463` for the four GCC ones, `gpucc-volcano.c:577-593` for the GPU one), so nothing has to vote them.

**F7. IOVA window properties are mostly unread.** `qcom,iommu-dma-addr-pool` and `qcom,iommu-geometry` sit on 42 nodes. The SMMU
layer does not read them, three drivers do: IPA (`modules/modem-data/dataipa/.../ipa.c`), adsprpc (`modules/audio-sensors/dsp-kernel/dsp/adsprpc.c:8256`)
and icnss2 (`modules/wlan-bt/wlan/platform/icnss2/main.c:5291`, and `qcom,iommu-geometry` at `:4540`). icnss2 hands the window to the WLAN
firmware. For all other nodes the IOVAs come from the whole aperture. Pineapple dropped these properties too. Phone: SMMU
context faults in `dmesg` during the first minute and after camera, display and video use, and WLAN SMMU faults while Wi-Fi
connects and carries traffic.

**F8. CPU thermal pause has no driver.** `/soc/qcom,cpu-pause` (`qcom,thermal-pause`) provides the `cpuN-pause` cooling devices
that 13 cooling maps name. `thermal_pause.ko` needs the WALT scheduler hooks and is not ported, so the cooling devices never
register and those maps bind nothing. `qcom,cpufreq-cdev` has no children (as in 6.1), so no CPU frequency cooling devices
exist either. Mitigation then rests on the userspace thermal engine, the GPU, CDSP and userspace cooling devices and the hardware
limits. A phone test comes first, no change before it. `ls /sys/class/thermal` lists the cooling devices. Then watch the temperatures
and clocks under sustained load.

**F9. RGB LED and its PWM have no driver.** `qcom,pwm-lpg` (three blocks on pmxr2230) and `qcom,tri-led` (`pmxr2230_rgb`, three
PWM channels). No driver in the set matches them. The core `drivers/leds/rgb/leds-qcom-lpg.c` of 6.18 matches other compatibles (`qcom,pm8350c-pwm` and the like) with a different binding. Phone: whether
the notification LED lights at all.

**F10. Two drivers match `qcom,pmic-glink`.** `modules/base/drivers/soc/qcom/qti_pmic_glink.c:760-762` (the vendor driver) and the
core `drivers/soc/qcom/pmic_glink.c:384`. It only matters if `CONFIG_QCOM_PMIC_GLINK` is built, which no defconfig sets.
Phone: the `driver` link of the `pmic_glink` device ends in `qti_pmic_glink`.

**F11. tsens reads a cell the nodes do not have.** `/soc/tsens0@c228000` and `/soc/tsens1@c229000`. With `nvmem-cells` present,
`modules/thermal-dcvs/drivers/thermal/qcom/tsens.c:1516-1530` reads the cell `tsens_chipinfo` and, on a match with four fixed
chip ids (`tsens.h:25-31`), raises the non-critical trips (`:1472-1496`). The nodes carry `tsens_itemp` (one fuse bit at qfprom
0x133), so each tsens logs "Not able to read tsens_chipinfo nvmem" and skips the update, which is the conservative direction.
A `tsens_chipinfo` cell needs a qfprom offset we do not have. Phone: `dmesg | grep tsens_chipinfo` (expected), and the trip
points of the cpu and gpu zones against `volcano-thermal.dtsi`. A phone test comes first, no change before it.

**F12. sys-pm-vx never probes.** `/soc/sys-pm-vx@c320000`. `modules/thermal-dcvs/drivers/soc/qcom/sys_pm_vx.c:808` binds, then `vx_probe`
(`:647`) matches again against `drv_match_table` (`:621-643`), which has no volcano entry, and returns -ENODEV. The driver is a
sleep-blocker debug aid. A volcano entry belongs in the driver with the RSC DRV names. Phone: `dmesg | grep -i sys-pm`.

**F13. cpucp-log never probes.** `/soc/qcom,cpucp_log@81840000`. `modules/thermal-dcvs/drivers/soc/qcom/cpucp_log.c:595` needs `qcom,log-type`
and returns -ENODEV without it. The sun 5.0 tree sets `qcom,log-type = <0>`. Not changed: it would map two 64 KiB buffers in
`cpucp_fw_region` and take mailbox channel 1, and whether the FP6 firmware logs there is carried over from 6.1. It is a debug
log. Phone: `dmesg | grep -i cpucp` shows the error today.

**F14. mmio-sram reg misparse.** `/soc/mmio-sram@17D09400`. `drivers/misc/sram.c:395-399` reads `reg` with the 1/1 cells of `/soc`
while the node has four cells, so the driver sees start 0 and size 0x17d09400. SCMI is not affected, it translates the child
`scmi-shmem@0` itself (`drivers/firmware/arm_scmi/shmem.c:219-231`). The node is identical on pineapple and kalama. Phone:
`dmesg | grep -i sram`, `grep sram /proc/iomem`, and that SCMI, cpufreq and bwmon are present.

**F15. Display BCM voter without `qcom,no-amc`.** `disp_bcm_voter` has `qcom,tcs-wait = <QCOM_ICC_TAG_AMC>`. Pineapple sets
`qcom,no-amc` for the same TCS layout. The 6.1 driver had the same logic and the tree never set it, so behaviour is unchanged.
`modules/base/drivers/interconnect/qcom/bcm-voter.c:613`. Phone: `dmesg` for "Error sending AMC RPMH requests".

**F16. PMIC RTC is read-only.** `modules/base/drivers/rtc/rtc-pm8xxx.c:472`. The node has neither `allow-set-time` nor an offset
cell, so `set_time` returns -ENODEV (same as 6.1 and pineapple). Whether the RTC should follow the network time is a
decision, not a binding fix.

**F17. A pin state in the pmiv0104 overlay is ignored.** `charger_skin_therm_default` (gpio6) spells `bias-high-impedence` with an e
and has no function, so the generic parser ignores the whole state. Other targets spell it `bias-high-impedance`
(`cliffs-pm8550b.dtsi`, `anorak-pmic-overlay.dtsi`). The state sits in `volcano-pmiv0104.dtsi`, which feeds the overlay, and 6.1
behaved the same. Phone test first: read the charger skin temperature ADC channel and see whether it works without the state.
Then fix the spelling. That changes `dtbo.img`, so it is a release change and not part of this branch.

**F18. `qcom,cci0` and `qcom,cci1` cells (fixed in C8).** `/soc/qcom,cci0@ac15000` is a simple-bus without `#address-cells` and
`#size-cells`, and the SKU overlay adds a child `qcom,ois@0` with a `reg`. The core warns once for the first parent without
cells, so the node hid behind others. Both CCI nodes now carry 1 and 1, the values the walk up to `/soc` finds, and the
`explicit-cells` check fails for any node with a `reg` under a parent without cells.

**F19. `lpass_bt_swr` stub.** `/soc/spf_core_platform/lpass_bt_swr@31E0000`. The base node holds only the compatible and an empty
child, the real properties are in `volcano-audio-bt-swr.dtsi`, which the FP6 build does not apply. The probe fails with
-EINVAL on every boot (`lpass-bt-swr.c:422-468`) and logs one line. No effect on audio.

**F20. Two copies of the dt-binding headers.** `dts/include/dt-bindings` and `modules/base/include/dt-bindings` differ in
`ipcc.h`, `rpmh-regulator-levels.h`, `rpmh.h`, `thermal_qti.h`, `qti-smmu-proxy-dt-ids.h`, `spmi-vadc.h` and `hv-haptics.h`.
Every name the tree uses has the same number in both copies (checked for the whole of `volcano-thermal*.dtsi`, for example).
The QMI sensor ids 80 to 86 of `thermal_qti.h` mean different sensors, and no volcano node uses those names.

**F21. Nodes whose driver is not in the 6.18 set.** The table marks them "no driver". They are debug or test nodes (coresight, the
Gunyah test clients, smp2p rdbg, limits-stat, core hang detect, the vendor hook stubs), nodes of features that were not ported
(memory offline, USB audio offload, HDCP, SMMU proxy sender, MPM sleep counter, GIC routing, the qrng hardware RNG), and three
nodes of the secure world side: `qcom,qseecom` and `qcom,tee-shared-memory-bridge` are replaced by `qseecom_proxy`, smcinvoke and the
shmbridge code inside qcom-scm, none of which reads a node, and `qcom,tz-log` has no driver.
`modules/camera-video/securemsm-kernel/smmu-proxy` holds headers only. The coresight modules are left out on purpose (the
packaging deny list). Phone: check that the secure world services the system uses (key attestation, gatekeeper, weaver) work
and that `dmesg` shows no qseecom or smcinvoke errors.

**F22. Audio and camera pointers.** Audio: `pineapple.c:2811-2813` takes `qcom,sku-model` or `qcom,model` for the sound card
name depending on the `adsp_variant` fuse, so the user space audio configuration must carry the name this phone reports
(`cat /proc/asound/cards`, and the "adsp variant fuse reg value" line from `adsp-loader.c`). The `fsa4480` USB-C analog switch is
registered as a type-c mux and nothing in the tree looks it up (same as 6.1). `adsp-dtb-fw-names` is absent on purpose.
Camera: `cam_icp_soc_common.c:166` finds no `fw-pas-id` and falls back to 33, which the 6.1 pineapple node sets too. If the ICP
firmware does not load, check this first. CPAS has no `qcom,axi-port-camnoc` children (`cam_cpas_soc.c:302`), so CAMNOC
bandwidth is not voted through interconnect (same as 6.1). Watch for low frame rates or CAMNOC underruns in `dmesg`.

**F23. Nodes that exist only in the SKU overlay.** The display `qcom,dsi-display-primary`, `qcom,wb-display@2`, the pmiv0104
`qcom,lcdb@f700` and `qcom,wled@f500`. The camera `qcom,cam-res-mgr`, flash, actuator, sensor, eeprom and ois nodes under the two CCI
buses. The audio `aw882xx_smartpa` nodes, the wcd9378 codec and its two slaves, the eight `qcom,msm-cdc-pinctrl` nodes and seven
of the nine `qcom,audio-ref-clk` nodes. No misread was found in them. A later fix for any of them has to go into the overlay,
because the base has no copy of the node to compensate in.

**F24. Values the bootloader and firmware supply.** The DCVS ddr tables and the memlat ddr monitors pick their `ddr4` or
`ddr5` child by `qcom,ddr-type` against `ddr_device_type` of `/memory`, which the bootloader must set (phone: no "Unable to find
freq tbl prop" in `dmesg`). `qcom,pmu` has no `qcom,long-counter`, so counters are 32 bit, which is harmless at the 8 ms
sampling rate. There is no fast-path dcvs child, so memlat votes through the slow path.

### Unread 6.1-only properties

These stay in the tree because the 6.1 drivers (or the overlay) wrote them and nothing in the 6.18 set reads them. None
changes behaviour. The notable ones: the microSD `vdd-supply`, `vdd-io-supply` and `qcom,vdd-*` levels (the driver now reads
`vmmc` and `vqmmc`, the old names come from the board overlay), `dummy-supply` of the eUSB2 PHY, `qcom,bcm-voters` and
`qcom,bcm-voter-names` of the interconnect providers, `reg-name` of the clock controllers, `qcom,bus-id` of the SPMI arbiter,
`reg-supply` of the GX GDSC, `qcom,dcvs-hw-type`, `qcom,bus-width` and `qcom,dcvs-path-type` of the dcvs nodes (read from the
parent where needed), `qcom,iommu-vmid`, `qcom,can-sleep` of an I2C PMIC, `qcom,ipa-platform-type-msm`, `qcom,audiopkt-ch-name`,
the unused timing properties of the eswin touch node, and `snps,disable-clk-gating` (F4).
